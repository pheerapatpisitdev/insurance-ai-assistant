# ชุดประกันที่จัดเอง (Bundles) — เอกสารออกแบบ

วันที่: 2026-09-04
สถานะ: รอผู้ใช้ตรวจทาน

## 1. เป้าหมาย

ทุกวันนี้เครื่องคำนวณให้ผู้ใช้จัดแบบประกันเองได้อยู่แล้ว (เลือกแบบหลัก → แพ็กเกจ → ติ๊กสัญญาเพิ่มเติม → ใส่ทุน)
แต่ชุดที่จัดไว้ดีแล้วไม่ถูกเก็บ ต้องประกอบใหม่ทุกครั้ง และตัวแทนที่ยังไม่ชำนาญอาจจัดผิดเงื่อนไข

เอกสารนี้ออกแบบ **"ชุดจัดเอง" (bundle)**: ชุดสำเร็จรูปที่เจ้าของโปรเจกต์กำหนดไว้ล่วงหน้า
ผู้ใช้เลือกชุด → เลือกแผนย่อย → กรอกอายุ เพศ งวดชำระ → ได้เบี้ยทันที โดยไม่ต้องตัดสินใจอะไรอีก

ชุดแรกคือ **มรดกเพื่อครอบครัว** 10 แผนย่อย

## 2. ขอบเขต

### อยู่ในขอบเขต
- ชุดจัดเองปรากฏเป็นตัวเลือกในช่อง "แบบประกันหลัก" ข้าง ๆ แบบประกัน 5 แบบเดิม
- แต่ละชุดมีแผนย่อยหลายแผน แต่ละแผนล็อคทุนของสัญญาหลักและสัญญาเพิ่มเติมไว้ตายตัว
- ผู้ใช้แก้ทุนไม่ได้ และเพิ่ม/ลดสัญญาเพิ่มเติมไม่ได้
- กฎ **"ครบทั้งชุด หรือไม่ขายเลย"** (ข้อ 6)
- ข้อความสรุปสำหรับคัดลอก ระบุชื่อชุดและแผนย่อย
- ชุด "มรดกเพื่อครอบครัว" พร้อมข้อมูลครบ 10 แผน

### นอกขอบเขต
- หน้าจัดการชุดใน `/admin` — ผู้ใช้ยืนยันว่าให้เพิ่มชุดใหม่ในโค้ดทุกครั้ง
- ปรับทุนตามงบลูกค้าอัตโนมัติ (ผู้ใช้เลือกใช้แผนย่อยแบบทุนคงที่แทน)
- เทียบหลายชุดข้างกันบนหน้าจอเดียว
- ให้ AI เลือกแผนย่อยให้จากความต้องการลูกค้า

## 3. ชุดแรก: มรดกเพื่อครอบครัว

สัญญาหลัก **Life Protect+ 100 — ชำระเบี้ยครบอายุ 99 ปี** (`LIFEPROTECT` / `WLF99H`) ทุน 200,000 บาททุกแผน
บวก **DCI (สัญญาเพิ่มเติมโรคร้ายแรง)** ที่ทุนต่างกันไปตามแผนย่อย

แต่ละแผนขายด้วยชื่อที่บอกทุนรวมที่ครอบครัวได้รับ ไม่ใช่หมายเลขแผน

| ชื่อที่ขาย | ทุนหลัก | ทุน DCI | ทุนรวม |
|---|---|---|---|
| มรดก 1 ล้าน | 200,000 | 800,000 | 1,000,000 |
| มรดก 2 ล้าน | 200,000 | 1,800,000 | 2,000,000 |
| มรดก 3 ล้าน | 200,000 | 2,800,000 | 3,000,000 |
| มรดก 4 ล้าน | 200,000 | 3,800,000 | 4,000,000 |
| มรดก 5 ล้าน | 200,000 | 4,800,000 | 5,000,000 |
| มรดก 6 ล้าน | 200,000 | 5,800,000 | 6,000,000 |
| มรดก 7 ล้าน | 200,000 | 6,800,000 | 7,000,000 |
| มรดก 8 ล้าน | 200,000 | 7,800,000 | 8,000,000 |
| มรดก 9 ล้าน | 200,000 | 8,800,000 | 9,000,000 |
| มรดก 10 ล้าน | 200,000 | 9,800,000 | 10,000,000 |

ตรวจกับกฎในระบบแล้ว ทั้ง 10 แผนถูกต้อง:
- ทุนหลัก 200,000 ≥ ขั้นต่ำของแบบ (150,000)
- ทุน DCI อยู่ในช่วง 200,000 – 10,000,000 (แผน 10 ใช้ 9,800,000 เหลือเพดาน 200,000)
- `WLF99H` เป็นแพ็กเกจลำดับที่ 6 จึงไม่ติดข้อห้ามของแพ็กเกจ Health Ultra / Health Extra (ลำดับ 7 และ 8) ที่บังคับทุน DCI ไว้ที่ 200,000

ข้อจำกัดที่ตามมาจากกฎเดิม (ระบบต้องบอกผู้ใช้ให้ชัด ไม่ใช่คิดเบี้ยครึ่ง ๆ กลาง ๆ):
- **อายุ 20 – 65 ปีเท่านั้น** — DCI รับอายุ 20–65 ส่วนแบบหลักรับ 0–80 ช่วงที่ขายได้จริงคือส่วนที่ทับกัน
- **เบี้ยรวมรายเดือนต้องไม่ต่ำกว่า 1,000 บาท** — แผนย่อยต้น ๆ กับอายุน้อยจะจ่ายรายเดือนไม่ได้
  (ชาย 20 ปี แผน 1 = 358.20 บาท/เดือน, หญิง 20 ปี แผน 5 = 989.64 บาท/เดือน ทั้งคู่ต่ำกว่าขั้นต่ำ)

**ผลประโยชน์กรณีเสียชีวิตรวมทุน DCI ด้วย** เพราะ DCI จ่ายในกรณีเสียชีวิตเช่นกัน
กติกาข้อนี้เขียนไว้ที่กฎของสัญญาเพิ่มเติมเอง (`paysOnDeath` ใน `data/rules/*.json`) ไม่ใช่ที่ชุด
สัญญาที่ติดธงนี้และซื้อได้จริงในใบเสนอนั้น จะถูกบวกเข้าไปทั้งสองบรรทัด ไม่ว่าจะจัดเองหรือมาจากชุด
ส่วนตัวคูณของ Life Protect+ 100 (จ่ายเพิ่มอีก 1 เท่าเมื่อเสียชีวิตก่อนอายุ 60) คูณเฉพาะทุนสัญญาหลัก

ตัวอย่างแผน "มรดก 3 ล้าน": ก่อนอายุ 60 ได้ 3,200,000 บาท (200,000 × 2 + 2,800,000)
ตั้งแต่อายุ 60 ได้ 3,000,000 บาท ซึ่งตรงกับชื่อแผนพอดี

## 4. โครงสร้างข้อมูล

ชุดหนึ่งชุด = ไฟล์ JSON หนึ่งไฟล์ใน `data/bundles/` — ไม่มีตัวเลขเบี้ยอยู่ในไฟล์นี้เลย
มีแต่การอ้างอิงไปยังแบบประกันและทุน เบี้ยยังคิดจาก `data/rates/*.json` ชุดเดิม
พอตารางเบี้ยฉบับใหม่มา (ฉบับปัจจุบัน `A2026-1` หมดอายุ 2027-03-31) ชุดนี้อัปเดตตามเองโดยไม่ต้องแก้อะไร

`data/bundles/legacy-family.json`:

```json
{
  "code": "LEGACY_FAMILY",
  "name": "มรดกเพื่อครอบครัว",
  "planCode": "LIFEPROTECT",
  "variant": "WLF99H",
  "tiers": [
    { "no": 1, "name": "มรดก 1 ล้าน", "sumAssured": 200000, "riders": [{ "code": "DCI", "sumAssured": 800000 }] },
    { "no": 2, "name": "มรดก 2 ล้าน", "sumAssured": 200000, "riders": [{ "code": "DCI", "sumAssured": 1800000 }] }
  ]
}
```

ตัวอย่างข้างบนตัดมาสองแผน ไฟล์จริงมีครบ 10 แผนตามตารางในข้อ 3
`name` คือชื่อที่ใช้ขายและใช้แสดงผลทุกที่ — เจ้าของชุดตั้งเองได้ ไม่ผูกกับสูตร
มีเทสต์คุมไว้ว่าชื่อของทุกแผนต้องตรงกับทุนรวมจริงของแผนนั้น กันพิมพ์ผิดตอนเพิ่มแผนใหม่

`tiers[].riders` ใช้รูปแบบเดียวกับ `RiderInput` ที่เครื่องคำนวณรับอยู่แล้ว
ชุดในอนาคตจึงใส่สัญญาเพิ่มเติมชนิดอื่นได้โดยไม่ต้องแก้โครงสร้าง
เช่น MEB ใช้ `{ "code": "MEB", "plan": 5000 }` หรือ iHealthy Ultra ใช้ `option` / `territory` / `coverage`

ชนิดข้อมูล `Bundle`, `BundleTier` ประกาศไว้ใน `src/calc/types.ts` ต่อจากชนิดอื่น

## 5. โมดูลใหม่

`src/calc/bundles/registry.ts` — ทะเบียนชุด คู่ขนานกับ `src/calc/plans/registry.ts`
- `listBundles(): { code, name }[]`
- `getBundle(code): Bundle | undefined`

`src/calc/bundles/quote.ts` — แปลงชุดเป็นอินพุตของเครื่องคำนวณ แล้วบังคับกฎครบทั้งชุด
- `bundleQuoteInput(bundle, tierNo, who): QuoteInput` — `who` คือ `{ age, sex, mode }`
- `quoteBundle(bundle, tierNo, who, today?): QuoteResult | undefined` — เรียก `quote()` ตัวเดิมแล้วบังคับกฎข้อ 6

**เครื่องคำนวณ (`src/calc/quote.ts`) ไม่ถูกแก้เลย** ชุดจัดเองเป็นเพียงชั้นบาง ๆ ที่ประกอบอินพุตให้
กฎทุกข้อ — ช่วงอายุ ทุนขั้นต่ำ/สูงสุด ความสัมพันธ์ระหว่างสัญญา เบี้ยรายเดือนขั้นต่ำ — จึงบังคับใช้เหมือนเดิมโดยอัตโนมัติ

## 6. กฎ "ครบทั้งชุด หรือไม่ขายเลย"

ชุดสำเร็จรูปต่างจากการจัดเอง: ถ้าส่วนใดส่วนหนึ่งซื้อไม่ได้ ชุดนั้นก็ไม่ใช่ชุดที่ออกแบบไว้อีกต่อไป
ระบบเดิมจะคิดเบี้ยเฉพาะส่วนที่ซื้อได้แล้วขึ้นคำเตือน ซึ่งเสี่ยงให้ตัวแทนเผลอเสนอชุดที่ไม่ครบ

`quoteBundle` จึงตรวจผลลัพธ์จาก `quote()` ว่าเข้าเงื่อนไขข้อใดข้อหนึ่งต่อไปนี้หรือไม่
1. มีรายการใดที่ `eligible === false`
2. มีคำเตือนระดับ `error` — ยกเว้นเบี้ยรายเดือนต่ำกว่าขั้นต่ำ (ดูย่อหน้าถัดไป)

ถ้าเข้าเงื่อนไข ให้คืนผลที่ `totalAnnual` และ `totalModal` เป็น 0 พร้อมเพิ่มคำเตือนระดับ `error`
รหัส `BUNDLE_INCOMPLETE` ข้อความ `ชุด<ชื่อชุด> — <ชื่อแผน> ใช้กับกรณีนี้ไม่ได้`
โดย **ยังคงรายการทั้งหมดไว้** เพื่อให้ผู้ใช้เห็นว่าบรรทัดไหนที่ติดปัญหาและติดด้วยเหตุผลอะไร
คำเตือนเดิมจากเครื่องคำนวณไม่ถูกลบ ผู้ใช้จึงเห็นทั้งสาเหตุ (`อายุรับประกัน 20 - 65 ปี`) และผลสรุป

**เบี้ยรายเดือนต่ำกว่าขั้นต่ำไม่นับเป็นชุดไม่ครบ** ทุกรายการยังซื้อได้และชุดยังเป็นชุดเดิม
ติดแค่งวดชำระนี้เท่านั้น ระบบจึงคิดเบี้ยตามปกติและแสดงตัวเลขจริง แล้วปล่อยให้คำเตือนเดิมทำหน้าที่บอก
ถ้าซ่อนตัวเลขไว้ ตัวแทนจะไม่รู้ว่าขาดอีกเท่าไหร่ ซึ่งเป็นข้อมูลที่ใช้ตัดสินว่าจะเสนอเป็นรายปีหรือขยับขึ้นแผนถัดไป

หน้าเว็บซ่อนยอดเบี้ยรวมเมื่อพบคำเตือน `BUNDLE_INCOMPLETE` แทนที่จะแสดง 0.00 บาท
และไม่แสดงคำเตือนนั้นซ้ำในรายการคำเตือนด้านล่าง เพราะพาดหัวสีแดงบอกไปแล้ว เหลือไว้แต่สาเหตุ

## 7. หน้าเว็บ

`FormState` เพิ่มสองฟิลด์: `bundleCode: string | null` และ `tier: number`

**ช่องแบบประกันหลัก** — เพิ่ม `<optgroup label="ชุดจัดเอง">` ไว้บนสุด เหนือกลุ่มแบบประกันเดี่ยว
ค่าของตัวเลือกชุดใช้รูปแบบ `bundle:LEGACY_FAMILY` เพื่อไม่ให้ชนกับรหัสแบบประกัน

**เมื่อเลือกชุด** ฟอร์มเปลี่ยนไปดังนี้
- ช่องที่สองเปลี่ยนจาก "แพ็กเกจ" เป็นรายชื่อแผนของชุด เช่น `มรดก 3 ล้าน` — ตัวแทนกับลูกค้าจึงเรียกแผนด้วยคำเดียวกัน
  ส่วนทุนที่อยู่เบื้องหลังชื่อ แจกแจงอยู่ในตารางผลลัพธ์แล้ว
- ช่องอายุเสนอเฉพาะช่วงที่ชุดขายได้จริง (`bundleAgeRange` = ช่วงของแบบหลัก แคบลงตามสัญญาเพิ่มเติมทุกตัวในชุด)
  ผู้ใช้จึงเลือกอายุที่ชุดรับไม่ได้ตั้งแต่แรกไม่ได้ ส่วนกฎครบทั้งชุดในข้อ 6 ยังคุมกรณีที่ช่วงอายุจับไม่ได้ เช่น เบี้ยรายเดือนต่ำกว่าขั้นต่ำ
- ซ่อนช่องทุน ช่องเบี้ยที่ต้องการ (basis) และรายการสัญญาเพิ่มเติมทั้งหมด
- คงไว้เฉพาะ อายุ เพศ งวดชำระ
- ความโปร่งใสมาจากสองที่: ชื่อแผนในช่องเลือกบอกทุนทุกก้อน และตารางผลลัพธ์ทางขวาแจกแจงชื่อแบบหลัก
  แพ็กเกจ และสัญญาเพิ่มเติมพร้อมเบี้ยรายบรรทัดอยู่แล้ว จึงไม่ทำกล่อง "ชุดนี้ประกอบด้วย" ซ้ำอีกกล่อง
  เหลือไว้เพียงบรรทัดบอกว่าทุนในชุดนี้แก้ไม่ได้

**เมื่อสลับกลับไปแบบประกันเดี่ยว** ฟอร์มกลับสู่พฤติกรรมเดิมทั้งหมด และรีเซ็ตสัญญาเพิ่มเติมเหมือนการสลับแบบประกันในปัจจุบัน

**แผงผลลัพธ์** ไม่ต้องแก้โครงสร้าง เพราะรับ `QuoteResult` อยู่แล้ว
เพิ่มเพียงหัวเรื่องชื่อชุดและแผนย่อย และการซ่อนยอดรวมตามข้อ 6

**หัวหน้าเพจ** บรรทัดที่แสดงชื่อแบบและเวอร์ชันตารางเบี้ย ให้แสดงชื่อชุดแทนเมื่อเลือกชุดอยู่
เวอร์ชันตารางเบี้ยยังคงเป็นของแบบประกันที่ชุดอ้างอิง

## 8. ข้อความสรุป

`summaryText` รับพารามิเตอร์ที่สามเพิ่มเข้ามาเป็นทางเลือก `bundle?: { name: string; tier: string }`
โดย `tier` คือชื่อแผน เมื่อมีค่า ให้แทรกบรรทัดแรกเป็น `ชุดมรดกเพื่อครอบครัว — มรดก 3 ล้าน` เหนือบรรทัดชื่อแบบประกันเดิม
ส่วนที่เหลือของข้อความคงเดิมทุกบรรทัด รวมถึงผลประโยชน์กรณีเสียชีวิตและเวอร์ชันตารางเบี้ย

- `bundleQuoteInput` ประกอบอินพุตถูกต้อง: `planCode`, `variant`, ทุนหลัก และสัญญาเพิ่มเติมตรงกับแผนย่อยที่เลือก
- `bundleQuoteInput` คืน `undefined` เมื่อไม่พบแผนย่อยตามหมายเลขที่ส่งมา ไม่ใช่โยน error และ `quoteBundle` ก็คืน `undefined` ตามไปด้วย
- กฎครบทั้งชุด: อายุ 66 → ยอดรวมเป็น 0 มีคำเตือน `BUNDLE_INCOMPLETE` และยังมีรายการ DCI ที่ `eligible === false` ให้เห็น
- ชาย 20 ปี แผน 1 งวดรายเดือน → ยังคิดเบี้ยจริง 358.20 บาท พร้อมคำเตือน `MIN_MONTHLY` และไม่มี `BUNDLE_INCOMPLETE`
- ชุดที่ขายได้ตามปกติต้องไม่มีคำเตือน `BUNDLE_INCOMPLETE`
- ผลลัพธ์ของชุดต้องเท่ากับการจัดเองด้วยมือทุกสตางค์ (เทียบกับ `quote()` ที่ป้อนอินพุตเดียวกัน)

**`tests/golden/legacy-family.test.ts`** — ค่ายึดที่คำนวณจากตารางเบี้ยต้นฉบับโดยตรง (หน่วยบาท, รายปี)

## 10. ลำดับการทำ

1. ชนิดข้อมูล `Bundle` / `BundleTier` ใน `src/calc/types.ts` และไฟล์ `data/bundles/legacy-family.json` ครบ 10 แผน
2. `src/calc/bundles/registry.ts` พร้อมเทสต์
3. `src/calc/bundles/quote.ts` (การประกอบอินพุต + กฎครบทั้งชุด) พร้อมเทสต์
4. Golden test เทียบค่ายึดในข้อ 9
5. หน้าเว็บ: ช่องเลือกชุด แผนย่อย การซ่อนช่องที่ไม่ใช้ และกล่อง "ชุดนี้ประกอบด้วย"
6. ข้อความสรุปและการซ่อนยอดรวมเมื่อชุดไม่ครบ
7. `npm run verify` ให้ผ่านทั้งหมด
