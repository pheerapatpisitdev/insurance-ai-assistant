# หน้า CRM และ Dashboard สำหรับผู้ช่วย AI ประกัน — เอกสารออกแบบ

วันที่: 2026-09-15
สถานะ: รออนุมัติ

## 1. เป้าหมาย

เพิ่มหน้า `/admin/crm` ในหลังบ้านเดิม ให้เจ้าของเพจเปิดดูตอนเช้าแล้วรู้สองอย่างในหน้าเดียว:

1. **บอททำงานดีแค่ไหน** — คนทักกี่คน ได้เบี้ยไปกี่คน สนใจสมัครกี่คน หล่นหายตรงไหน
2. **วันนี้ควรทักใครกลับ** — รายชื่อลูกค้าที่บอทคุยด้วย พร้อมปุ่มเปิดแชท

## 2. สิ่งที่พบจากการตรวจ source และฐานข้อมูล

ตารางและฟังก์ชันสำหรับ CRM **ถูกออกแบบและสร้างไว้ครบแล้วใน Supabase** แต่โค้ดในแอปไม่เคยเรียกใช้เลย

ตารางที่มีอยู่ (ทุกตารางว่าง 0 แถว):

| ตาราง | คำอธิบายที่กำกับไว้ในฐานข้อมูล |
|---|---|
| `ins_conversations` | หนึ่งแถวต่อหนึ่งบทสนทนา: มาจากไหนและไปได้ไกลแค่ไหน `user_hash` ถูกล้างหลัง 90 วัน |
| `ins_events` | เกิดอะไรขึ้นในบทสนทนา: เก็บประเภทกับตัวเลขเท่านั้น ไม่เก็บคำพูดลูกค้า |
| `ins_leads` | คนที่ขอสมัครหรือขอคุยกับคน `psid_cipher` เข้ารหัสด้วย `pgp_sym_encrypt` และล้างหลังปิดการขาย 180 วัน |
| `ins_unanswered` | คำถามที่บอทไม่มีคำตอบ เก็บเป็นประโยคที่โมเดลเรียบเรียงใหม่ ไม่ผูกกับใคร เก็บ 30 วัน |
| `ins_ad_daily` | ตัวเลขโฆษณารายวันต่อชิ้น เขียนโดย Routine จาก Marketing API ไม่มีข้อมูลส่วนบุคคล |

ฟังก์ชัน `SECURITY DEFINER` ที่มีอยู่แล้วและยังไม่ถูกเรียก:

- `ins_open_conversation(channel, page_id, user_hash, source, ad_id, ref, referral, entry_payload)`
- `ins_attribute(conversation, source, ad_id, ref, referral)`
- `ins_record(conversation, events jsonb, product, unanswered jsonb)`
- `ins_open_lead(conversation, psid, passphrase, stage, product, form_ref)`
- `ins_get_lead_psid(lead, passphrase)`
- `ins_prune()`

ตาราง `ins_chat_sessions` มีคอลัมน์ `conversation_id` เตรียมไว้แล้ว และโค้ดไม่เคยเขียนลงไป

ยืนยันด้วย `grep` ว่าใน `src/` เรียกฟังก์ชันทั้งหกตัวนี้ **0 ครั้ง** และอ้างถึง `conversation_id` **0 ครั้ง**

**สรุป: งานนี้คือการต่อสายไฟที่เดินไว้แล้ว ไม่ใช่การออกแบบฐานข้อมูลใหม่**

## 3. ข้อจำกัดที่ยอมรับแล้ว

- **ไม่มีข้อมูลย้อนหลัง** `ins_chat_sessions` เก็บแค่ 6 ข้อความล่าสุด และทิ้งหลัง 24 ชั่วโมง
  ([`session.ts:9-11`](../../../src/lib/chat/session.ts)) ข้อมูลใน CRM จะเริ่มนับจากวันที่ deploy
- **ไม่เก็บคำพูดลูกค้า** ตามที่ `ins_events` ออกแบบไว้ ยกเว้น `ins_unanswered` ที่เก็บคำถามซึ่งโมเดลเรียบเรียงใหม่แล้วและไม่ผูกกับตัวบุคคล
- **ไม่เก็บชื่อและรูปลูกค้าลงฐานข้อมูล** — ดึงสดจาก Graph API ตอน render หน้า
- **เฟสแรกอ่านอย่างเดียว** ไม่มีปุ่มแก้สถานะ ไม่มีโน้ต ไม่มีการส่งข้อความออกจากหน้านี้

## 4. ขอบเขต

### อยู่ในขอบเขต

- ขั้นที่ 1: การบันทึก — ต่อ RPC เดิมเข้ากับ `conversation.ts` และ webhook
- ขั้นที่ 2: ที่มาจากโฆษณา — รับ `messaging_referrals` และเก็บ `ad_id`
- ขั้นที่ 3: หน้า `/admin/crm` — ตัวเลขสรุป, กราฟ funnel, กราฟรายวัน, กราฟรายชั่วโมง,
  เทียบ Life Protect กับ iHealthy, ตารางลูกค้า 3 แท็บ
- ขั้นที่ 4: ต้นทุนต่อลูกค้า — ดึงยอดใช้จ่ายโฆษณาเข้า `ins_ad_daily`

### นอกขอบเขต

- แก้สถานะ เพิ่มโน้ต ส่งข้อความ — เฟสถัดไป
- แจ้งเตือนเมื่อมีคนสนใจสมัคร (`ins_alert_settings` มีอยู่แล้วแต่ยังไม่ทำ)
- ช่องทาง Web และ Voice — `Channel` ยังเป็น `"facebook"` อย่างเดียว
- การแก้ปัญหาความปลอดภัยจาก `HANDOFF-TO-CLAUDE.md` — แยกเป็นงานของตัวเอง

## 5. ขั้นที่ 1 — การบันทึก

### 5.1 หมุดหมายของบทสนทนา

เขียนลงคอลัมน์ที่มีอยู่แล้วใน `ins_conversations` โดยใช้สัญญาณที่โค้ดมีอยู่:

| คอลัมน์ | เกิดเมื่อ | สัญญาณในโค้ดปัจจุบัน |
|---|---|---|
| `priced_at` | บอทบอกเบี้ย | `answer.priced` ใน [`common.ts:97`](../../../src/lib/assistant/common.ts) |
| `form_sent_at` | บอทส่งลิงก์ใบสมัคร | `slots.formSent` |
| `form_done_at` | ลูกค้าบอกว่ากรอกเสร็จ | `saysFormDone()` ใน [`lifeprotect/answer.ts:77`](../../../src/lib/assistant/lifeprotect/answer.ts) |
| `agent_replied_at` | ตัวแทนพิมพ์เอง | `agentTyped(event)` ใน [`conversation.ts:56`](../../../src/lib/facebook/conversation.ts) |
| `handover_at` | ลูกค้ากด "สนใจสมัคร" | `WANTS_IN` ใน [`common.ts:78`](../../../src/lib/assistant/common.ts) |
| `stalled_at` | ส่งข้อความตามแล้วเงียบ | `ins_sweep_followups` |
| `messages` | ทุกข้อความของลูกค้า | นับเพิ่มทีละ 1 |
| `model_calls` | ทุกครั้งที่เรียกโมเดล | นับเพิ่มทีละ 1 |

### 5.2 คำศัพท์ของเหตุการณ์

`ins_events(kind, product, data)` — ค่า `kind` ที่นิยามในงานนี้:

| kind | เมื่อไหร่ | data |
|---|---|---|
| `open` | บทสนทนาเริ่ม | `{source, ad_id}` |
| `ask` | ลูกค้าพิมพ์หรือกดปุ่ม | `{}` |
| `quote` | บอทเสนอเบี้ย | `{age, sex, plan, sum, premium, mode}` |
| `card` | ส่งรูปการ์ดราคา | `{plan}` |
| `switch` | เปลี่ยนผลิตภัณฑ์ | `{from, to}` |
| `wants_in` | กด "สนใจสมัคร" | `{}` |
| `form_sent` / `form_done` | ใบสมัคร | `{}` |
| `followup` | ส่งข้อความตาม | `{stage}` |
| `agent` | ตัวแทนเข้ามาตอบ | `{}` |
| `failed` | บอทตอบไม่ได้ / งบหมด | `{reason}` |

`data` ต้องไม่มีคำพูดของลูกค้าเด็ดขาด

### 5.3 จุดที่ต้องแก้ในโค้ด

1. **`webhook/route.ts`** — ส่ง `entry.id` (page id) เข้า `handle()` เพราะ
   `ins_open_conversation` ต้องการ `p_page_id` และตอนนี้ route ไม่ได้ส่งต่อ
2. **`session.ts`** — `loadSession` คืน `conversation_id` ด้วย และ `saveSession` เขียนกลับ
   ถ้าแถวหมดอายุตาม `MAX_AGE_HOURS` ให้เปิดบทสนทนาใหม่
3. **`conversation.ts`** — เรียก `ins_open_conversation` เมื่อเริ่ม, สะสมเหตุการณ์ระหว่างเทิร์น,
   เรียก `ins_record` ครั้งเดียวตอนจบเทิร์น, เรียก `ins_open_lead` เมื่อถึง `wants_in` หรือ `form_sent`
4. **โมดูลใหม่ `src/lib/chat/record.ts`** — ห่อ RPC ทั้งหมด หน้าที่เดียวคือบันทึก
   ต้อง **ไม่โยน error ออกไป** ทุกกรณี: การบันทึกล้มต้องไม่ทำให้ลูกค้าไม่ได้คำตอบ

### 5.4 กฎการทำงาน

- การบันทึกทั้งหมดเกิดหลังจากส่งข้อความให้ลูกค้าเรียบร้อยแล้ว
- ทุก error จากการบันทึกถูกจับและ log ไม่ส่งต่อ
- หนึ่งเทิร์นเรียก `ins_record` ครั้งเดียว ไม่ใช่ครั้งละเหตุการณ์

## 6. ขั้นที่ 2 — ที่มาจากโฆษณา

ตอนนี้ระบบรับ webhook แค่ 3 field ([`oauth.ts:28`](../../../src/lib/facebook/oauth.ts))
และ type `Messaging` ไม่มีช่องอ่านข้อมูลโฆษณา จึงยังไม่รู้ว่าลูกค้ามาจากแอดตัวไหน

ต้องทำ:

1. เพิ่ม `messaging_referrals` ใน `SUBSCRIBED_FIELDS`
2. เพิ่มช่อง `referral` และ `postback.referral` ใน type `Messaging` ([`events.ts`](../../../src/lib/facebook/events.ts))
3. อ่าน `ref`, `ad_id`, `source` ส่งเข้า `ins_open_conversation` หรือ `ins_attribute`
4. เพจที่เชื่อมอยู่แล้วต้อง subscribe field ใหม่ — ตรวจว่าต้องกดเชื่อมใหม่หรือเรียก API ซ้ำได้

**ยังไม่ยืนยัน:** รูปแบบที่ Meta ส่งข้อมูลโฆษณามาสำหรับ Click-to-Messenger ต้องอ่านเอกสาร
Meta ฉบับปัจจุบันก่อนเขียนโค้ด ไม่เดาจากความจำ

## 7. ขั้นที่ 3 — หน้า `/admin/crm`

### 7.1 โครงสร้าง

```
/admin/crm
├── ตัวเลือกช่วงเวลา: วันนี้ · 7 วัน · 30 วัน
├── แถวตัวเลขสรุป
│   คนทักเข้ามา · ได้เบี้ยไป · สนใจสมัคร · กรอกฟอร์ม · บอทตอบไม่ได้ · ค่า AI
│   (เพิ่ม "ต้นทุนต่อลูกค้า" เมื่อขั้นที่ 4 เสร็จ)
├── กราฟ "ลูกค้าหล่นหายตรงไหน"
│   ทักเข้ามา → บอกอายุ/เพศ → ได้เบี้ย → สนใจสมัคร → กรอกฟอร์ม
├── เทียบ Life Protect กับ iHealthy (ตัวเลขชุดเดียวกัน แยกตามแผน)
├── กราฟรายวัน (แท่งซ้อน: ทัก / ได้เบี้ย / สนใจ)
├── กราฟรายชั่วโมง (ช่วงเวลาที่คนทักเยอะ)
└── ตาราง 3 แท็บ
    ├── ลูกค้าล่าสุด
    ├── ต้องตามต่อ  (สนใจสมัคร หรือ เงียบหายหลังได้ราคา)
    └── คำถามที่ตอบไม่ได้
```

### 7.2 คอลัมน์ในตารางลูกค้า

ลูกค้า (รูป+ชื่อ) · แผน · อายุ/เพศ/ทุน · เบี้ยที่เสนอ · มาจากแอดไหน · สถานะ · ล่าสุด · ปุ่มเปิดแชท

### 7.3 ชื่อและรูป

Server Component อ่าน lead จากฐานข้อมูล → ถอด PSID ด้วย `ins_get_lead_psid` →
เรียก Graph API `/{psid}?fields=name,profile_pic` ด้วย Page token → แสดงผล

- ไม่เขียนชื่อหรือรูปลงฐานข้อมูล
- ดึงเฉพาะแถวที่อยู่บนหน้าจอ
- คนที่ `psid_cipher` ถูกล้างแล้วแสดงเป็น "ลูกค้าเก่า" และไม่มีปุ่มเปิดแชท
- Graph API ล้มต้องไม่ทำให้ทั้งหน้าพัง แสดงแถวโดยไม่มีชื่อแทน

### 7.4 ปุ่มเปิดแชท

ลิงก์ไปกล่องข้อความของเพจ ไม่ส่งข้อความใด ๆ จากหน้านี้

### 7.5 การยืนยันตัวตน

ทุก Server Action และทุกฟังก์ชันที่อ่านข้อมูลต้องเรียก `requireAdmin()` **ในตัวฟังก์ชันเอง**
ไม่พึ่ง guard ที่ `layout.tsx` อย่างเดียว ตามข้อค้นพบ P1 ใน `HANDOFF-TO-CLAUDE.md`

## 8. ขั้นที่ 4 — ต้นทุนต่อลูกค้า

ต้องการยอดใช้จ่ายโฆษณารายวันใน `ins_ad_daily` เพื่อคำนวณ
`ยอดใช้จ่ายของแอด ÷ จำนวน lead จากแอดนั้น`

**ติดขัด:** `SCOPES` ปัจจุบันคือ `["pages_show_list", "pages_messaging", "pages_manage_metadata"]`
([`oauth.ts:18`](../../../src/lib/facebook/oauth.ts)) ไม่มี `ads_read`

ผลที่ตามมา:

- ต้องเพิ่ม scope และให้เจ้าของเพจเชื่อมบัญชีใหม่
- อาจต้องผ่าน App Review ของ Meta — **ยังไม่ยืนยัน** ต้องตรวจเงื่อนไขปัจจุบันก่อน
- คอมเมนต์ใน `oauth.ts` ระบุว่าตั้งใจขอสิทธิ์ให้แคบเพื่อให้ App Review เล็ก การเพิ่ม scope ขัดกับเจตนาเดิม

จึงแยกเป็นขั้นสุดท้าย ถ้าติด App Review หน้า CRM ยังใช้งานได้เต็มที่โดยไม่มีคอลัมน์ต้นทุน

## 9. ความเป็นส่วนตัว

- ตัวเลขสถิติเก็บตลอด ไม่มีกำหนดลบ
- ตัวระบุตัวตนถูกล้างตามที่ `ins_prune()` กำหนดไว้แล้ว: `user_hash` 90 วัน,
  `psid_cipher` 180 วันหลังปิดการขาย, `ins_unanswered` 30 วัน
- ต้องตั้ง Cron เรียก `ins_prune()` เพราะตอนนี้ไม่มีอะไรเรียก
- **ต้องแก้หน้า Privacy** ให้ตรงกับสิ่งที่ระบบเก็บจริง
- **ข้อควรพิจารณา:** PDPA ให้สิทธิ์ลูกค้าขอลบข้อมูลของตน เฟสแรกไม่มีปุ่มลบในหน้าจอ
  จึงต้องมีวิธีลบรายคนอย่างน้อยผ่าน SQL และบันทึกวิธีไว้

## 10. การทดสอบ

- `record.ts` — ทุก error ถูกกลืน ไม่มีทางโยนออก
- `conversation.ts` — behavior เดิมทุกข้อยังผ่าน: dedup, human takeover, follow-up, rate limit
- หมุดหมายแต่ละอันถูกตั้งครั้งเดียว ไม่ทับของเดิม
- บทสนทนาที่หมดอายุแล้วเริ่มแถวใหม่ ไม่ต่อของเก่า
- หน้า CRM: ไม่มีข้อมูลต้องไม่พัง, Graph API ล้มต้องไม่ทำให้ทั้งหน้าพัง

## 11. สิ่งที่ยังยืนยันไม่ได้

- รูปแบบข้อมูลโฆษณาที่ Meta ส่งมาสำหรับ Click-to-Messenger
- เงื่อนไข App Review ของ `ads_read` ในปัจจุบัน
- เพจที่เชื่อมอยู่แล้วต้องกดเชื่อมใหม่หรือไม่ เมื่อเพิ่ม subscribed field
- `ins_prune()` ลบอะไรบ้างแน่ ยังไม่ได้อ่าน definition
- ค่า `stage` ที่ `ins_open_lead` รับ มีค่าอะไรได้บ้าง

ต้องตรวจทุกข้อก่อนเขียนโค้ดส่วนที่เกี่ยวข้อง ห้ามเดา
